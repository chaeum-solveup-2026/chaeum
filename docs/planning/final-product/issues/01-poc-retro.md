# 01: PoC 회고: 무엇이 잘 됐고 무엇을 버릴까

Type: grilling
Status: resolved
Blocked by: None (can start immediately)

## Question

예선 PoC(chaeum-poc)에서 본선 제품으로 가져갈 것, 버릴 것, 다르게 할 것은 무엇인가? 근거: chaeum-poc 의 docs/RESOURCES.md, docs/review/REVIEW-LOG.md, docs/metrics, 커밋 기록, 워크플로 중단과 재시작 경험.

## Answer

2026-10-28 grilling 으로 결정(찬규님).

가져갈 것과 규칙:
- 해석기 로직, 품목 사전, 정답 표, 측정 하네스는 본선 제품으로 옮긴다. test 세트는 마일스톤에만 측정하고 개선에는 dev 세트만 쓴다. 정답 표는 에이전트 초안이므로 본선 발표에서 수치를 쓰기 전에 해석기를 만들지 않은 사람(성은님)이 검수한다
- 화면 작업 순서는 "성은님 목업의 화면 구조와 동작을 먼저 옮기고, 그다음 디자인 토큰"으로 고정한다(PoC 첫 UI 는 반대로 해서 다시 고쳤다)
- 담당자 인증과 데모 초기화, 시드는 첫 tracer bullet 티켓에 넣는다(PoC 는 인증이 스펙에 있었는데 빠졌고, 데모 DB 상태 blocker 가 마지막에 나왔다)
- 에이전트 운영: 티켓 하나에 에이전트 하나 + tdd + 가벼운 게이트(테스트와 인수 조건). 다관점 리뷰는 마일스톤마다 1라운드. 병렬은 파일이 겹치지 않을 때만 worktree 로

다시 정할 것(버릴 것이 아니라 시연용 단순화):
- 요청-수령 2단계(배정 없음) -> 기능 범위(02)
- 분류 모델 슬롯만 있음 -> 기능 범위(02), 아키텍처(03). 조사 결과는 05
- 연수구 파일 데이터 -> 공공데이터(06, 해결: 15139148 API)
- 로컬 Docker 배포 -> 아키텍처(03), NCP 확정(10)

용어: PoC 용어집을 출발점으로 가져오되, 가져오기 전에 검토한다(티켓 12). 새 용어(배정 단계 등)는 기능 범위(02)에서 정해질 때 추가한다.
